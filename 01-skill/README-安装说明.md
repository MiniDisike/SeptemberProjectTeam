# task-warden · 安装与使用说明

一句话：**开工时把你的原话逐字锁住，每轮按固定公式申报"你要的 vs 我给的"，
交付≠需求就逼出偏差申报单并把选择权交回你，收尾出"需求→交付→成本"主表。**

治三件事：需求漂移、验收糊弄、调好的手感被改坏。

---

## 1. 包里有什么

| 文件 | 作用 |
|---|---|
| `SKILL.md` | **skill 本体**：三角色 + 每轮公式 + 铁律 + 红线 |
| `warden.mjs` | 主脚本：`init` / `record` / `check` / `report` / `history` |
| `bill.mjs` | 成本：从 DSH 会话日志算**真实** token / 墙钟 / 模型（AI 编不了） |
| `selftest.mjs` | 自检：15 条负控（漂移/糊弄/替用户拍板）必须全抓到，3 条正控必须不误伤 |
| `templates/params-<工程>.yml` | 你那个项目的档位清单（23 个，已逐个验证能从源码读到） |

零第三方依赖，只要 **Node 18+**。

## 2. 装到 DSH

```
<HOME>\.dsh\skills\task-warden\
    SKILL.md  warden.mjs  bill.mjs  selftest.mjs  templates\
```

**不需要杀进程、不需要重启** —— DSH 会热加载 skill 目录，装完当轮就能看到。
（"保证被读到"靠的是 `~/.dsh/AGENTS.md` 里的硬规则，因为那是每个会话第一轮必然注入的地方。）

只要某个工程用：放到 `<工程>\.dsh\skills\task-warden\`（工程级优先于用户级）。

## 3. 三步走

```powershell
$W = "<HOME>\.dsh\skills\task-warden\warden.mjs"

# ① 开工：建骨架，然后把用户原话**逐字**填进 .warden/SPEC.md
node $W init

# ② 每轮：按公式申报（值由脚本读源码，你报的会对账）
node $W record --req R1 --status in_progress --delivered "多面体球骨架" `
     --evidence "src/plugins/anchor_orb.rs:29" --why "开始搭"

# ③ 收尾：说"完成"之前
node $W check      # exit 0=过 1=有问题 2=用法错
node $W report     # 生成 .warden/REPORT.md 给用户看
```

改完 `warden.mjs` 必须跑 `node selftest.mjs`。

## 4. 每轮公式（公式固定，问题每轮不同）

```
① 用户在这一点上逐字要的是什么？   → 引 SPEC 里的 R#，抄原话
② 我实际给的是什么？               → 具体到能验收
③ 一致吗？  一致→给证据记 done ｜ 不一致→**停**，填偏差申报单
④ 这一轮花了多少？                 → 脚本算，你别报
⑤ 用户损失了什么 / 额外拿到了什么？
```

**偏差申报单**五问 + 选项。默认推荐**必须**是「照原样做」；
推荐替代品而用户没表态 = 硬失败。**替代品在用户点头之前不算交付。**

## 5. 检查器逐条执行的硬规则

- 原话在会话日志里**逐字找不到**（被改写 / 只是我的总结）→ 硬失败
- 拿系统注入的文本冒充用户原话 → 硬失败
- 交付里出现用户明确说"不要"的东西，且没有**已获批准**的偏差申报单 → 硬失败
- 标 `deviated` 但没有申报单 → 硬失败
- 选项里没有「照原样做」/ 推荐替代品而用户未表态 / 理由 <20 字 → 硬失败
- **把用户原本的需求原文填进「用户决定」** → 硬失败（那是自己给自己签名）
- 用户没说过「用户决定」那句话，或那句话发生在交付**之前** → 硬失败
- `done` 没证据 / `partial` 没写缺哪半 / 需求从没被推进过 → 硬失败
- `--values` 报的档位值与源码不一致 → **拒收**（值以源码为准）
- 档位当前值与账本最后一版不一致 → 告警（它被改过了，去 `history` 看）

## 6. 诚实的边界

**它验的是「出处」和「结构」，不是「语义」。**
它能证明"用户确实说过这句话"，**不能**证明"这句话真的是在批准这个偏差"。
所以 `REPORT.md` 会把「用户决定」原文打出来给你看 —— **最后一道防线仍然是人眼**。

这不是偷懒，是这类东西的能力上限：语义批准无法机械判定。
把它当成"把荒诞摆在明面上"的工具，而不是"替我判断"的工具。

其它边界：
- `params.yml` 要人工声明（它不知道该盯哪些数据）。
- 依赖 DSH 的会话日志格式；格式大改时 `bill.mjs` 要跟着改，`selftest.mjs` 会先红。
- 只在 Windows + Node 22/24 上验证过。

## 7. 已知的坑（都是实测踩出来的）

- **系统注入也记成 `user/message`**：必须靠 `data.source.kind === "user"` 筛，
  否则 AI 把自己写的东西塞进 `agent-message` 就能冒充"用户原话"。实测分布：
  `user(129) / plugin(68) / agent-instructions(19) / subagent-settled(9) / agent-message(6)`。
- **DSH 会话日志是多帧 zstd**：Node 的 `zstdDecompressSync` 只解第一帧，
  必须按魔数 `28 B5 2F FD` 切帧逐帧解（一个 321 帧的会话，只解第一帧会少 99% 的内容）。
- **会话目录是三层的**：`sessions/<工作区编码>/<会话id>/session.v3.jsonl.zstd`，
  工作区编码规则 `D:\a\b` → `--D-a-b--`。
- **`DSH_SESSION_ID` 环境变量直接给了当前会话 id**，不用猜。
