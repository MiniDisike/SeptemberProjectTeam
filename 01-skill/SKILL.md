# 需求监督员（需求锚定 · 交付审查 · 数据账本）

**它治三个已经反复发生的事故：**

1. **需求漂移** —— 开工时说要 A，收尾给的是 B，而且还是"B 也是里面要用的"，你没法说他。
   典型现场：你要多面体球并解释了为什么，它回头问你「1. 立方体（推荐）2. 多面体 3. 光球」。
   全权限的话它就直接做立方体了 —— **造汽车要一个齿轮，它给你一个正方形，说做完了。**
2. **验收糊弄** —— 一小时的活、上亿 token，关键问题只解决了半个，其它在原地踏步，最后交一张含糊的账。
3. **昂贵调参被无声破坏** —— 花一天调好的手感、打好的地基，加个新功能就没了，还找不回来。

配套文件就在本 skill 目录：`warden.mjs`（主脚本）、`bill.mjs`（成本）、`selftest.mjs`（自查）、`templates/`。

## 0. 七个角色，什么时候用

| 角色 | 干什么 | 什么时候 |
|---|---|---|
| **监督员** | 把用户原话**逐字**锁进 `SPEC.md`，一轮结束时核对"你要的 vs 我给的" | **开工第一件事**，以及一轮结束时（准备提交/汇报） |
| **审查** | 出"需求 → 交付 → 成本"主表；标出 未做 / 半交付 / 已交付 / **多给的** | 说"完成"之前 |
| **记录** | 每轮的档位数据 + 这一轮花了多少；数据被改坏时能查到改了几次、哪版更精细。**要改一件已经确认完成的东西时，先 `snapshot` 备份**（`record` 里有硬闸门拦着） | 一轮结束时；**每次要动已确认完成的东西之前** |
| **支线守门员** | 架构总图：哪条支线从没被碰过 / 几轮没动了 | 一轮结束时，和"下一轮做什么"之前 |
| **提问闸门（脑子）** | 拦住"不该问的问题"——已经答过的、文档里能查到的、该自己定的 | **每次想开口问你之前** |
| **资料员**（2026-09-16 加） | 事实性问题**不靠猜**：自己去查（官方文档 / 搜索 / 源码），**给出去处**，并把结论**落到某条 R#** 上。**被交办"改已确认完成的东西"时，先出依据与影响面** | 遇到"这个库/格式/API 到底怎么用"、或要引用外部事实时 |
| **方向员**（2026-09-16 加） | **大局观 + 考虑周到**：横向给"工程还能往哪些方向做"，**排优先级**；每个方向必须指回一条用户原话或已登记痛点，指不回就标 `AI提案`。**核心交付是「维度清单」**（见 0.8）——写软件前把"这次该一次考虑到的维度"列全，适用的交代、不适用的写明为什么。跟主代理结论同构又没有独有项 ⇒ 自己标「未提供独立视角」，那一轮不算它的劳动。**并接手「档位备份」职责**：动关键数据前 `snapshot`、收尾 `diff` 一遍看"哪个函数没了 / 哪个值变了" | 一轮结束时定"下一轮做什么"之前；**动手产出任何东西之前**；每次要动被盯的档位之前 |

## 0.4 一轮结束时的**两张清单**（开工的【需求清单】/ 收尾的【结果清单】+对账）

用户 2026-09-17 提出（**公开版已隐去原文**）：核心诉求是本轮任务开始给需求清单、结束时给结果清单并对账——
**从来没有实现过**。⇒ 这是他反复说、却一直没兑现的一条，所以现在是**一轮结束时的固定动作**（一轮 = 任务完成、准备提交/汇报，不是每一步）：

```powershell
node <skill目录>\warden.mjs needs   [--session <本窗口>] [--last 5]   # 开工：需求清单
node <skill目录>\warden.mjs results [--session <本窗口>] [--last 5]   # 收尾：结果清单 + 对账
```

- **开工先给需求清单**：本窗口最近 N 条原话 → 各自的归宿（需求 R# / 非要求 / 已答过 / **还没归宿**）
  → 本轮要做的 R# 及各自现在的状态。没有归宿的原话**先补归宿再开工**（否则没有对账的锚）。
- **收尾给结果清单 + 对账**：每条 R# 的交付 / 证据 / **还差哪半**；最后一行是口径：
  `需求 N 条 → 已交付 / 半交付 / 在做 / 没做`，`原话 N 条 → 按归宿分类`，
  **没归宿的原话当成"对账缺口"逐条列出来**（那正说明"他说过的没有对应的结果行"）。
- **只给本轮、有上限**（默认最近 5 条）：不许把全历史砸进去 —— 全历史是 `report` 的事。
- 这两张清单要**贴给用户看**（不是只写进文件）：他要的就是"开始看需求、结束看结果、两边对得上"。

## 0.45 交接的时机（**不是每一步都写**）

**一轮 = 任务完成、准备提交/汇报**，不是每一步。交接只在以下两个时机写：

1. **一轮结束时**（任务完成、准备提交/汇报）——写交接，总结这一轮做了什么、还差什么。
2. **上下文即将压缩时**（约 60% 以上使用量）——写交接，防止压缩后丢失关键信息。

**压缩后或新任务开始时**：看上一轮的交接——但**只看一次**，看完就继续干活。
**不要每次都看交接**：新窗口/新任务开始时，旧交接可能已经是两三轮以前的了，
按旧交接说"应该停止"是 BUG——那已经是过去的事了，当前任务可能已经往前走了好几轮。

## 0.5 **两层记忆**（最重要的一节，其它都可以不看）

用户的原话有**两层**，混在一起就会出事故：

| 层 | 文件 | 性质 | 能不能改写 |
|---|---|---|---|
| **第一层 · 总目标** | `SPEC.md` | 开项目的原因、需求。**可以和 AI 一起探讨、最后汇总** | **可以**——标注 `归属: 用户原话 / 用户+AI汇总 / AI提案` |
| **第二层 · 窗口传递** | `VOICE.jsonl` | 用户在**每个窗口**说过的**每一句话**，逐字 | **一个字都不许动** |

**第二层比第一层重要。** 为什么：第一层是**汇总过的**，汇总本身就会丢信息。
用户的原话丢进窗口、很快被忽视，最后交付一个**四不像**。

> **实测事故（2026-09-16）**：用户 16:05:08 已经回答过"木材工艺链是什么"——
> 「木材工艺链是我的一个比喻…**这个功能不是要去掉，反而是要加强**…把这个**加进总目标**」，
> 并在 16:10 派了专门调研的子代理。**12 分钟后，AI 又把这个问题问了一遍。**
> 而 AI 当时的依据是"ARCH 里这条支线 0 轮"——它把自己的分类法当成了事实。

```powershell
node <skill目录>\warden.mjs voices        # 抽取/更新第二层（自动，不靠 AI 记得写）
node <skill目录>\warden.mjs voices 木材    # 查用户说过什么
```

**规矩：任何"第一层"里的条目，只要能指回一句用户原话就必须指回去；指不回去的，
老实标 `AI提案` —— 不要写成"用户原话"。**（`warden quotes` 会全项目扫这种冒名顶替。）

## 0.6 **提问闸门**：想开口问你之前，先过两道关

用户的核心诉求：查到已答过就不再问；有些问题不值得占用用户注意力。

所以"问用户"是一个**需要审批的动作**，两道关都要过：

### 第一关 · 机械（脚本做）
```powershell
node <skill目录>\warden.mjs ask "你想问的问题"
# exit 1 = 拦下了（用户很可能已经答过）→ 不许问，去读那些原话
# exit 0 = 机械层没查到 → 进第二关
```
它同时会查**工程文档里有没有现成答案**——能查到的先去读，别问。

> 诚实边界：中文没空格，而且**用户的答案里往往没有问句里的词**（问"木材工艺链是有意放着还是被漏掉了"，
> 答的是"木材工艺链是我的一个比喻…反而要加强"）。所以脚本只能"捞出候选"，
> **判不准**。真实判断归第二关。

### 第二关 · 脑子（派独立子代理，脚本做不了）
派一个**独立子代理**当脑子，**只给它**：问题 + `.warden/VOICE.jsonl` + `SPEC.md` + `ARCH.md` + 工程目录，
**不给你的结论**。要求它回答三件事：

1. **这问题该不该占用用户的注意力？**（凡是"我懒得查/懒得定"的，不该问）
2. **答案能不能自己查、自己定？** 能 → 给出结论 + 依据，写进交付，**别问**。
3. **非问不可的话，怎么问才对？** 必须给「你要的 vs 我给的」并排对照 + 含「照原样做」的选项。

```powershell
node <skill目录>\warden.mjs ask --verdict decide --reason "文档里已有答案，我自己定了"
node <skill目录>\warden.mjs ask --verdict ask    --reason "这是总目标层的取舍，必须用户拍板"
```

**这一层就是"松紧的度"**：太松 → 项目跑偏；太紧 → 用户被问烦。
度不该由规则定，该由这个专门用脑子的角色定。

## 0.7 **脑子默认 1 个；只有触发条件成立才派第 2 个**

用户 2026-09-2x 逐字：「（用户原话已隐去 —— 公开版不留逐字）」

⚠ **这一条推翻了下面那张旧表**（"总目标 / 架构 / 交付验收 → 2 个脑子（高风险，必须两个）"）。
一次性派两个的代价是双份成本，而且第二个脑子在**没有触发条件**时只是在复述第一个 ——
那正是 §一①「差异化」判据要抓的"摆设"：**一个角色的价值 = 它提出的、别人提不出来的东西**。

### 现在的规则（`BRAIN_TRIGGERS`，单一事实源在 `warden.mjs`）

| 什么时候 | 几个脑子 |
|---|---|
| 随手的小改动 | 0（不必审） |
| **按需**——只在下面三种触发条件之一成立时才派 | **1**（**必须**用 `--trigger` 记下是哪种） |
| 触发条件同时成立两个以上 | 2（同理，必须每个都记 `--trigger`） |

| 触发条件 | 判据 | 第 2 个脑子多交什么 |
|---|---|---|
| `conflict` | 两份判断（或两个来源）**结论不一致** | 独立判**哪边成立** + 可机检证据；不许折中成"两边都有道理" |
| `shallow` | 第 1 个给的问题**太笼统、没证据、或明显没看完** | 每条判断必须附**能在文件里 grep 到的原话** |
| `explore` | 需要"**还有哪些做法 / 哪些坑**"，不是"这行不行" | 除 accept/reject 外另给 **≥3 条别的做法**（做法/代价/什么条件下更好） |

```powershell
node <skill目录>\warden.mjs brain brief --artifact .warden/ARCH.md        # 第 1 个（默认）
node <skill目录>\warden.mjs brain brief --artifact .warden/ARCH.md --trigger conflict   # 加派第 2 个
node <skill目录>\warden.mjs brain record --artifact .warden/ARCH.md --brain A `
     --verdict reject --issues "总目标被截断,漏7条支线"
node <skill目录>\warden.mjs brain record --artifact .warden/ARCH.md --brain B --verdict reject `
     --issues "…" --trigger conflict
node <skill目录>\warden.mjs brain        # 状态：没审 / 单审（默认）/ 一致 / 一致·互补 / ★冲突·未裁决
```

**派脑子时必须**：只给材料（产物 + `VOICE.jsonl` + `SPEC.md` + `ARCH.md` + 工程目录），
**不给任何人的结论** —— 加派第 2 个时也一样：`--trigger` 只说"哪里需要更细 / 更多可能"，
**不许**把第 1 个的判决告诉它（给了判决，它就只是评论者，这次审查作废）。
要求它交回 `verdict: accept|reject` + `issues: 问题短名` + 逐条证据 + **`--claims`（可机检指控）**；
没有 `--claims` 的判决**既不能被证实也不能被驳倒**（`brain audit` 会明说"这次没复核任何东西"）。
**被审的产物里不许引用审查报告**（会破坏独立性 —— 实测被脑子抓到过）。

**脑子要能被看见**：`check` 会打一行 `[脑子] …`；台账里一个产物都没有时它会明说
"脑子从没跑过"—— 那是**要处理的事**，不是"没问题"。

### 冲突了怎么办：**不叫裁判拍板，让五个角色各按职责投票**

每个角色的票必须**从自己的职责出发**（记录不投"用户原话"的票 —— 那是监督员的活）：

| 角色 | 它的职责（投票依据） |
|---|---|
| 监督员 | 用户原话锚定：这事有没有违背用户**逐字**说过的话？ |
| 审查 | 证据：有没有证据支撑？自称算不算数？ |
| 记录 | 事实：数据/口径/数字对不对？能不能复算？ |
| 支线守门员 | 覆盖面：这会不会让某条支线被丢掉、或让项目跑偏？ |
| 提问闸门 | 用户注意力：这事值不值得占用用户的时间？ |

```powershell
node <skill目录>\warden.mjs vote cast --topic "ARCH能否定稿" --role 记录 --choice 不能 --reason "133 条里 32 条不属于本子项目，口径不对"
node <skill目录>\warden.mjs vote --topic "ARCH能否定稿"
#   → 多数：不能 ｜ 平票·未决 ｜ 缺席·未决 ｜ 有票没理由·未决
```

**未决（平票/缺席/没理由）→ 交给脑子继续想，不许硬定。** 脚本只计票，判断归脑子。

> 实测一例：议题「ARCH 能否定稿」→ 监督员/审查/记录/支线守门员都投"不能"，
> **提问闸门投"可以"**（它的职责是"值不值得占用用户时间"，不是"产物合不合格"）。
> **4:1 → 多数"不能"。** 注意这个"可以"不是错票 —— 五个角色本来就该看不同的东西。

## 0.8 **方向员的大局观：动手之前先要「维度清单」**（治"交付简陋"）

用户 2026-09-2x 逐字：「（用户原话已隐去 —— 公开版不留逐字）」

⇒ 于是"简陋"有了一个**可判定的定义**：

> **简陋 = 能适用的维度没交代，且没说明为什么不适用。**

### 谁干什么（两个角色缺一不可）

| 角色 | 在"维度"这件事上的活 |
|---|---|
| **资料员** | 把每条维度变成**有出处的事实**：这个库 / 格式 / 平台**实际**怎么要求（源码 + 行号、官方文档、实测命令 + 原样输出）。查不到就写"查不到" |
| **方向员** | 把事实变成**排好序的取舍**：每条标影响什么量（对**精确** ↑↓→ / 对**顺畅** ↑↓→）、成本、用户能感知到什么 |

### 清单（**可增补，不是穷举**；不适用的要写明理由）

目标与非目标 · 输入与校验 · 错误与失败态 · 边界与极端值 · 性能与资源 ·
结构与可维护性 · 测试与自检 · 用法与文档 · **观感与质感**（默认值 / 措辞 / 反馈 /
对齐 / 留白 / 动效）· 兼容与依赖 · 安全 · 后续可扩展点

⚠ 「该有的维度是跨功能通用的」**是断言不是事实（n=1）** —— 所以它是**可增补清单**、
不是闭集；每轮至少要报一条**清单上没有、但这次确实该考虑**的维度。

### 写代码要**并行派子代理**（用户：改善工作时间）

先切块 → 在**同一条消息**里同时派：

```powershell
# 按文件 / 模块切成**互不重叠**的块，然后同一条消息里同时派多个（run_in_background: true）
# 每块说清：改哪个文件、验收标准、不许碰别的文件
subagent_coder(prompt: "只改 src/a.rs：… 验收：cargo test a 全过；不许碰别的文件", run_in_background: true)
subagent_coder(prompt: "只改 src/b.rs：…", run_in_background: true)
```

- **别一个一个串行等** —— 那是工时的主要浪费；
- 切块必须**互不重叠**（并行改同一批文件会互相覆盖）；
- 每块收尾必须**贴原样自检输出**（跑不了就写清为什么跑不了）；
- 实现工程师（`subagent_coder`）是**唯一被允许写文件**的角色；资料员 / 方向员**只读**。

## 1. 一轮结束时的公式（**公式固定，问题每轮不同**）

这是整套东西的心脏。**一轮结束时**（任务完成、准备提交/汇报），按同一个公式走一遍（一轮 = 准备提交/汇报，不是每一步都走）：

```
① 用户在这一点上**逐字**要的是什么？   → 引 SPEC.md 里的 R#，抄原话
② 我这一轮实际给的是什么？            → 具体到能验收的东西
③ 一致吗？
     一致   → 给证据，记 status=done / in_progress
     不一致 → **停**。填偏差申报单（见 §2），默认推荐必须写「照原样做」
④ 这一轮花了多少？                    → 脚本自己算，你不用报
⑤ 用户损失了什么 / 额外拿到了什么？    → 一句话
```

**记一轮**（值由脚本从源码读，你报的会和源码对账，对不上就不许记）：

```powershell
node <skill目录>\warden.mjs record --req R1 --status in_progress `
     --delivered "多面体球骨架" --evidence "src/plugins/anchor_orb.rs:29" `
     --why "开始搭多面体" --values '{\"ripple_period\":1.30}'
```

- `--values` 可省；给了就一定对账（**源码为准**）。
- `--status` 只能是 `not_started | in_progress | done | partial | blocked | deviated`。
- `partial` **必须**加 `--missing_half "缺哪半"` —— 半成品不许含糊。

## 2. 交付 ≠ 需求时：偏差申报单（**不许悄悄换**）

你要的是多面体，它想给立方体？**可以，但必须写下来**，按固定格式：

```
你要的     <- 照抄 SPEC 的原话
要给的是   <- 实际打算做的
差异       <- 具体差在哪，要能看出损失
为什么必须偏离          <- ≥20 字
为什么这比照原样做更好   <- ≥20 字；说不出就说明根本不该改
你会损失什么            <- 必填
选项                    <- ≥2 个，**第 1 个必须是「照原样做」**
推荐                    <- 用户没表态前只能是 1
用户决定                <- 待定，直到用户真的说了
```

**硬规则（检查器逐条执行）：**

- 没填申报单就换 = **硬失败**；标了 `deviated` 却没有对应申报单 = **硬失败**。
- 推荐替代品而用户还没表态 = **硬失败**（**替代品在用户点头之前不算交付**）。
- 选项里没有「照原样做」= **硬失败**（不许把用户的原方案摘掉）。
- 理由 <20 字 = **硬失败**（"太麻烦""立方体也行"撑不住就不该改）。
- **拿用户原本的需求原文填进「用户决定」= 硬失败** —— 那是你在给自己签名。
- 用户没说过那句话 = **硬失败**；批准发生在交付**之前** = **硬失败**。

然后 `report` 会把这段并排打出来，让荒诞一眼可见：

```
  你要的     多面体球，面可以当落脚点，能画出不共面的笔
  要给的是   立方体      ← 面数 20→6，画不出不共面的笔
  为什么改   多面体实现太复杂了，立方体更简单更快
```

**唯一合法路径**：填单 → 把选项交回用户 → 用户明确表态 → 再交付。

## 3. 需求锁定（防漂移的地基）

`.warden/SPEC.md`，**append-only**：只许追加，不许改写已锁定的条目。

```markdown
## R1 · 多面体球作为落笔地基
- 原话: 我要的是一个多面体球，面可以当落脚点，能画出不共面的笔，不要立方体，也不要光球。
- 出处: session:<会话id>#<消息序号>
- 为什么: 他要的是"地基面"，要能切出很多面当落脚点；立方体只有 6 面
- 必须: 多面体；面可以当落脚点
- 不要: 立方体；光球
- 锁定: 2026-09-16
```

**「原话」必须是用户逐字说过的话。** 检查器会回到 `~/.dsh/sessions` 里核对：

- 只认 `data.source.kind === "user"` 的**真用户消息**。系统注入（AGENTS.md、运行期上下文、
  子代理通知）虽然也记成 `user/message`，但 kind 是 `plugin` / `agent-instructions` / `subagent-settled`…
  —— **不筛的话，AI 把自己写的东西塞进去就能冒充"用户原话"。**
- 去空白后逐字比对。改写过的、我替用户总结的，一律抓出来。

**为什么这条最值钱**：AI 不能悄悄把你的需求改写成它更想做的那个东西。
上下文几百万 token 之后，`SPEC.md` 是唯一还在讲你原话的地方。

## 3.5 **原话认领闸**（`claims`）—— 治"说过的事情被丢掉"（事故 I26）

**病根**：`VOICE.jsonl`（用户说过的，逐字在册）与 `SPEC.md`（我们在做的，R#）**没有任何连线**。
一条原话要变得"会被做"，必须有人**手工**把它写进 SPEC 成 R#；没人写就只躺在 VOICE 里，
而 `check` / `report` / `map` **三张表都不看它** ——
于是 `check` 会 exit 0 报「13 条需求全部一致」，却查不出**"从没进过清单"的要求**。这类缺口原来**连计数都没有**。

> 实测事故（I26）：用户提过角色说话要像网游聊天区的显示风格（角色名更小更细灰色、`某某某：XXX`）
> +「**真正在栏目里滚动的模样**」，查证：`SPEC/MAP/ARCH/REPORT/DEVIATIONS/ROUNDS` 里
> `滚动|栏目|聊天区|角色名|字号|字体` **命中 0**。在册，却无人负责。

`.warden/CLAIMS.jsonl`（**append-only**）就是那条连线，一行一条：

```json
{"voice":"<session-id>#20","kind":"需求","ref":"R13","why":"…","at":"…","by":"…"}
```

- `voice` = `"<session前缀>#<seq>"`，和 `VOICE.jsonl` 的 `session`+`seq` 对得上（session 允许**前缀**匹配）。
- `kind` 只有四种，**认领不是打勾，要说清这条原话变成了什么**：
  - `需求` → 它**已经**进了 SPEC，`ref` 写 `R#`（那个 R# 必须真的在 `SPEC.md` 里，否则 exit 2 ——
    不然闸门被静音了，东西还是没进清单）；
  - `非要求` → 闲聊、提问、情绪，`why` 必须写依据；
  - `已答过` → `ref` 写"指回哪一句"；`撤回` → 用户自己撤回了。

```powershell
node <skill目录>\warden.mjs claims              # 列未认领的真用户消息（默认 20 条，--all 全列），末尾「未认领 K / 共 M」
node <skill目录>\warden.mjs claims add --voice "<session-id>#20" --kind 需求 --ref R13 --why "…"
node <skill目录>\warden.mjs claims why --voice "<session-id>#20"   # 看这条原话认领成了什么
```

**水位线（关键设计，别改成全量硬失败）**：`.warden/CLAIMS.watermark.json` 记 `{"since":"…"}`。

- `check` **只对水位线之后**新增的 VOICE 条目要求认领：之后有未认领 → **exit 1** 并点出是哪几条；
  之前的未认领 → **只计数、只提示**，不失败。
- **为什么**：146 条历史原话不可能一次认领完，**全量硬失败会变成噪音、然后被无视**。
- 第一次运行（没有水位线文件）会自动把水位线设成"当前 VOICE 最新一条"，并打印
  `⚠ 已把水位线设在现在 —— 从现在起，新的用户原话必须被认领，否则 check 会失败`。
  历史那 143 条不会立刻把 check 弄红，但**从此不再漏新的**。
- `report` 主表尾部固定有一行 `原话认领：已认领 K / 共 M · **未认领 N**`（带时间戳），
  并列出**前 5 条**未认领的原话（截 40 字）。

**VOICE 的 `kind` 字段**：`syncVoices` 写新记录时带 `"kind":"user"`（老记录**一个字都不动**，
读取时缺省当 `user`）。为什么要有它：VOICE 原来只有 `session,seq,at,text,wrote`，
**无法从 VOICE 自身区分"用户真说"与"别处复述"**。

## 4. 档位账本（治"调好的手感被改坏"）

`.warden/params.yml` 声明**要盯住的数据**（花了很多轮才调好、最怕被改坏的那些值）：

```yaml
watches:
  - id: ripple_period
    label: 涟漪周期(秒)
    kind: rust_const          # 从源码读 const
    file: <你的工程>/src/plugins/example.rs
    name: RIPPLE_PERIOD_DEFAULT
  - id: rotate_deg_per_px
    label: 旋转灵敏度(度/px)
    kind: rust_const
    file: <你的工程>/src/plugins/example.rs
    name: ROTATE_DEG_PER_PX
```

`kind` 支持 `rust_const` / `json_field`（JSON 按点号路径）/ `jsonl_last`（JSONL 最后一条的字段）。

每轮 `record` 会把当前值**快照**进 `.warden/ROUNDS.jsonl`。于是：

```powershell
node <skill目录>\warden.mjs history ripple_period
```

```
轮次  值        本轮 token   本轮时间   为什么
   1  1.3       14,027,000  30m00s     开始搭多面体球
   2  1.3       32,019,500  10m00s     多面体太难，先做个立方体交差
                                              ↑ 花了 3200 万 token，值一个没动
```

**当前值和账本最后一版不一致 → 检查器会告警**：说明它被改过了，去 `history` 看改了几次、哪一版更精细。

`bill.mjs` 直接从 `~/.dsh/sessions/<工作区>/<会话id>/session.v3.jsonl.zstd` 读 **DSH 自己的**记录：

## 7. 铁律

1. **自称不算交付**。`done` 必须有证据；`partial` 必须写缺哪半。
2. **需求只认用户原话**。我的复述、我的总结、我的"优化"，都不算需求。
3. **替代品在用户点头前不算交付**。想换 → 填单 → 交回选择权。
4. **不许替用户签名**。把用户原本的要求抄进「用户决定」是伪造，会被抓。
5. **值以源码为准**。你记的档位值和源码对不上 → 拒收，重来。
6. **成本不用你报**，脚本算。你越少"报数"，账越可信。
7. **没跑过的不写通过**；失败原样贴，不许翻译成好消息。

### 红线（看到这些念头就停下）

- "这个更好，我直接改了" → 填偏差申报单。
- "用户应该不会介意" → 他不会介意的事，你更该问一句。
- "先做简单版本，回头再补" → 那就在 `ROUNDS` 里记 `partial` + `missing_half`，别记 `done`。
- "这个值我印象里是 1.3" → 脚本会去源码读；凭印象 = 会被拒收。
- "报告里这条我模糊写一下" → 检查器读的是字段，读不出结论就报错。

## 8. 已知边界（别把它当万能）

- **它验的是"出处"和"结构"，不是"语义"**：它能证明"用户确实说过这句"，
  不能证明"这句话真的是在批准这个偏差"。所以 `REPORT.md` 会把「用户决定」原文打出来给你看 ——
  **最后一道防线仍然是人眼**，这是设计上的诚实，不是缺陷。
- **它不判断工程品味**，只判断"需求写到没、证据有没有、值对不对"。
- **`params.yml` 要人工声明**：它不知道该盯哪些数据。第一次配的时候把"你心疼的那几个数"写进去。
- **多帧 zstd 依赖 DSH 的日志格式**；格式大改时 `bill.mjs` 要跟着改（`selftest.mjs` 会先红）。
- 只在 Windows + Node 22/24 上验证过。
